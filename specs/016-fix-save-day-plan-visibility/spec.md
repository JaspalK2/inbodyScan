# Feature Specification: Fix Save Diet Day Plan Visibility

**Feature Branch**: `016-fix-save-day-plan-visibility`  
**Created**: 2026-04-06  
**Status**: Draft  
**Input**: Clicking "Save day" on a diet plan day appears to do nothing — the saved plan does not appear in the Food & Meals "My Saved Meals" tab or in the Day Planner tab.

## User Scenarios & Testing *(mandatory)*

### User Story 1 — Saved Diet Day Appears in Food & Meals Tab (Priority: P1)

A user clicks "Save day" on a day row within a generated diet plan. The saved plan must immediately appear in the "My Saved Meals" → "Saved" sub-tab under "Saved Day Plans", without requiring a page refresh.

**Why this priority**: The save action is completely silent — no feedback, no appearance in the expected location. Users cannot tell if the save succeeded, making the feature effectively broken.

**Independent Test**: Click "Save day" on Day 1 of any diet plan → switch to the Food & Meals tab → click "Saved" → the "Saved Day Plans" section must show the newly saved plan with the name "Day 1 meal plan".

**Acceptance Scenarios**:

1. **Given** a diet plan with at least one meal containing food items, **When** the user clicks "Save day", **Then** the saved plan appears in the "Saved Day Plans" section of the Food & Meals "Saved" tab within 2 seconds — no page refresh required
2. **Given** a diet plan generated by the algorithmic engine (new format), **When** the user saves a day, **Then** the plan is saved with all 4 meal slots (breakfast, lunch, dinner, snack) and their macro values
3. **Given** the save action completes, **When** the plan appears in "Saved Day Plans", **Then** clicking it shows the meal slots with the correct calorie/macro summary

---

### User Story 2 — Saved Diet Day Appears in Day Planner Tab (Priority: P1)

The same saved day plan must also appear in the Day Planner tab under the saved plans list, immediately after saving.

**Why this priority**: The Day Planner is the primary location where users apply saved plans to specific calendar dates. If plans don't appear there, the entire save-and-plan workflow is broken.

**Independent Test**: Click "Save day" on Day 2 of a diet plan → switch to the Day Planner tab → the "Saved Day Plans" section at the bottom must include "Day 2 meal plan".

**Acceptance Scenarios**:

1. **Given** a successfully saved diet day, **When** the user navigates to the Day Planner tab, **Then** the saved plan is listed in the Day Planner's saved plans section
2. **Given** multiple diet days saved across different sessions, **When** the user views the Day Planner, **Then** all saved plans are listed, most recent first

---

### User Story 3 — Save Action Provides User Feedback (Priority: P2)

The "Save day" button must give clear feedback: a loading state while saving, and a visible confirmation (or error) once complete.

**Why this priority**: Even if the save is succeeding silently in the background, the lack of feedback makes users uncertain. A confirmation message prevents repeated clicking and double-saves.

**Independent Test**: Click "Save day" → button shows a spinner while saving → on success, a brief confirmation message ("Day saved!") appears → button returns to normal state.

**Acceptance Scenarios**:

1. **Given** the user clicks "Save day", **When** the save is in progress, **Then** the button shows a loading indicator and is disabled
2. **Given** the save completes successfully, **When** the user sees the result, **Then** a success confirmation is briefly shown (toast or inline message)
3. **Given** the save fails (e.g. network error), **When** the user sees the result, **Then** an error message is shown and the button returns to its normal state

---

### Edge Cases

- Diet plan day where all 4 meal slots have zero food items (new algorithmic format with sparse food database) — the "Save day" button must either be disabled, or show a message explaining nothing was saved
- Saving the same day twice — both entries should appear (no deduplication); the user should be aware they have duplicate entries
- Saving while already on the Food & Meals "Saved" tab — the list must update in place without losing the user's scroll position

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: After a successful save, the saved day plan MUST appear in the Food & Meals "Saved" tab's "Saved Day Plans" section without requiring a page reload
- **FR-002**: After a successful save, the saved day plan MUST appear in the Day Planner tab's saved plans list without requiring a page reload
- **FR-003**: The save operation MUST include all meal slots from the day, with their macro values (calories, protein, carbs, fat) correctly populated
- **FR-004**: The "Save day" button MUST be disabled and show a loading indicator while the save is in progress
- **FR-005**: A success confirmation MUST be shown to the user after a successful save
- **FR-006**: If the save fails, an error message MUST be shown and the button MUST return to its clickable state
- **FR-007**: The "Save day" button MUST be disabled (or show a warning) when none of the day's meal slots contain food items

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Saved day plan appears in both the Food & Meals "Saved" tab and the Day Planner tab within 2 seconds of clicking "Save day" — 0 cases where it remains invisible
- **SC-002**: 100% of save attempts produce either a visible success confirmation or a visible error message
- **SC-003**: Saved plans contain the correct meal slot names and macro values — 0 plans saved with blank/zero data when the source day had food items

## Assumptions

- The underlying save API endpoint (`POST /api/recommendations/day-plans`) is functioning correctly — the bug is in the frontend data flow, not in the backend
- The `["day-plans"]` query cache key is shared across the Diet tab, Food & Meals tab, and Day Planner tab within the same page — invalidating it should refresh all three
- The new algorithmic meal format produces non-empty food lists that satisfy the "at least one meal has foods" validation guard
- Success feedback will use the existing toast or alert mechanism already in the codebase — no new notification library needed
